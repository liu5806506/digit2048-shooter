| 项目 | 内容 |

### 1.1 关键发现：内部值是 **2 的指数**，不是显示的数字

这是理解整个游戏数值设计的前提。`GameConf.MAX_NUM = 32`，
而方块贴图按 `block/<v>.png` + 数字贴图 `block/<v>_1.png` 取用，
把 `block/<v>_1.png` 全部裁出来看，映射关系是：

| 内部值 | 显示 | 内部值 | 显示 | 内部值 | 显示 |
|---|---|---|---|---|---|
| 1 | 2 | 12 | 4K | 22 | 4M |
| 2 | 4 | 13 | 8K | 24 | 16M |
| 3 | 8 | 14 | 16K | 26 | 64M |
| 4 | 16 | 15 | 32K | 28 | 256M |
| 5 | 32 | 16 | 64K | 30 | 1024M |
| 6 | 64 | 17 | 128K | 31 | 2048M |
| 7 | 128 | 18 | 256K | **32** | **∞（皇冠无限）** |
| 8 | 256 | 20 | 1024K | | |
| 9 | 512 | | | | |
| 10 | 1024 | | | | |
| **11** | **2048** | | | | |

即：**显示数字 = 2^内部值**，从 2^12 起改用 K/M 记法（按 1024 进制，
所以 2^20 = 1048576 显示成 `1024K`，2^30 显示成 `1024M`），2^32 封顶显示为 ∞。

含义：
* 游戏标题里的 **2048 恰好是内部值 11**，是明确的里程碑（`DOT_SCORE` 里也有 2000/3000 等里程点）。
* 内部值 32 是"满级"，贴图是皇冠 ∞ —— 引导文案第 5 条称它为「万能方块（可与任何数字合成）」。
  **注意：本版本的合并逻辑里并没有实现万能匹配**（见 §14），∞ 只能和 ∞ 合并。
* 因为合并是"指数 +1"，所以**每合成一次，显示数字翻倍**，视觉反馈极强。

## 2. 坐标系：天花板才是"地面"

这是复刻时最容易做错的地方。

* `GameConf.DIRECT = 1`（`UserModel.data.direct` 默认 1）。
* `Block.vy` 的 setter：`this.y = calcPosY(vy)`，而 `calcPosY(v) = v * YGAP(105)`。
  即**逻辑行 y 越大，屏幕 y 越大（越靠下）**。
* 但重力 `checkDown()` 把方块往 **y = 0** 压实，`blockIn()` 也是从"最小的空位"开始放。

结论：**逻辑 y = 0 在屏幕顶部**，方块被射上来后贴顶堆叠，堆栈**自上而下生长**，
发射器在棋盘下方，堆到 y = 7（贴近发射器）就算死。

实测佐证（浏览器里读 Laya 世界坐标）：

| 元素 | 屏幕坐标（750×1334 设计分辨率） |
|---|---|
| 棋盘背板 `game/bg2.png` | (15, 234) 尺寸 720×1096 |
| 5 条轨道 `game/track.png` | x = 40 / 174 / 309 / 443 / 577，y = 252，尺寸 121×845 |
| 发射轨道 `game/trackPrepare.png` | y = 1209 |
| 发射器中的方块 | y ≈ 1168 |
| 面板 play 区 | x 39 → 710，y 252 → 1181 |

所以 y=0 的方块画在 y≈252（顶），y=7 的方块画在 y≈1061（底），发射器在 y≈1209（最低）。

### 2.1 几何常量

```
XGAP = 122        列间距（设计像素，棋盘局部）
YGAP = 105        行间距
touchBox 缩放 1.1  →  屏幕列宽 CELL_W = 134.2，行高 CELL_H = 115.5
startBox 位于 grid 局部 y = 870（发射轨道）
born（发射器）位于 touchBox 局部 (314, 870)
```

## 3. 发射与落点判定

### 3.1 `checkIn(value, x)` —— 这一列会把方块放到哪一行

```js
checkIn(value, x) {
  for (let i = height - 1; i >= 0; i--) {      // 从最下面那格往上找
    if (blocks[x][i]) {
      if (i < height - 1) return i + 1;        // 往上放一层
      else if (blocks[x][i].value === value) return i + 1;   // ← 顶入
      else return -1;                          // 满了，不能用
    }
  }
  return 0;                                    // 整列空
}
```

**顶入机制（重要）**：如果一列已经堆满到 y = 7，但最顶上那格的值**恰好等于**要射入的值，
则返回 `8`（越界一行）。方块会被放到 y = 8，与 y = 7 立刻合并（互为四邻），
合并后腾出空间。也就是说**满列并非绝对死路**——只要顶块数值对得上就能"顶进去"化解。

这是刻意的救援设计，不是 bug（`blockIn` 里 `setBlock(block, x, 8)` 会把列数组临时撑到长度 9，
合并后 y = 8 又被置空）。复刻时务必保留。

### 3.2 `blockIn(value, x)` —— 真正落子

```
1. y = 该列最高的已占格 + 1（全空则 0）
2. 生成新方块 setBlock(x, y)，并把 this.cur = [block]（本轮待判定合并的方块）
3. 触发 NEW_BLOCK_DOWN（播放"射上去"的动画）
4. data.next = getNext()；触发 REFRESH_NEXT
5. 记录 data.preX/preY = (x, y)，触发 BLOCK_PRE（撤回道具要用）
6. saveBlocks()，this.combo = 0
```

飞行时长（原实现）：`duration = sqrt(|起点vy − 目标y|) * STEP_TIME(120)`，缓动 `sineOut`。
起点 vy 由玩家把方块往上拖多少决定：`vy_start = (发射器当前屏幕 y − 棋盘顶 y) / CELL_H`，
不拖时约为 8.28。

## 4. 重力

```js
checkDown() {
  for (每一列) {
    let off = 0;
    for (y = 0 .. height-1) {
      if (!blocks[x][y]) off++;                 // 累计上方空洞
      else if (off > 0) {                       // 有方块且上方有洞 → 往上落
        setBlock(block, x, y - off);
        setBlock(null,  x, y);
        触发 BLOCK_DOWN(block);
        downArr.push(block);
      }
    }
  }
  return 是否发生了移动;
}
```

因为 y 越小越靠"上"，重力实际是把方块**朝天花板压实**。
每次落子、每次合并之后都会先跑一遍重力，再判定合并。

## 5. 合并与级联

### 5.1 单次合并 `checkBlockCombine(target)`

```
1. 找 target 的四邻（上下左右，|dx|+|dy| == 1）中 值相同 且 本轮未合并过 的方块 → arr
   · 对角不算相邻！2×2 的同值方阵只会吃掉 3 个，留一个对角块
2. 若某个邻居自身能吃到的同值更多，就把合并中心换到它身上（贪心取最大团）
3. arr.length >= 1 时：
     arr 里补上 target 本身 → 共 N 个
     得分 += target.value * N          // 用指数值算分
     target.value += N - 1
     if (target.value > MAX_NUM) target.value = MAX_NUM     // 32 封顶
     arr[1..] 从棋盘移除
     combo += 1
     返回合并后的方块
```

合并结果数值表：

| 同时合并的等值方块数 N | 数值变化 | 得分 |
|---|---|---|
| 2 | +1（显示数字 ×2） | 值 × 2 |
| 3 | +2（×4） | 值 × 3 |
| 4 | +3（×8） | 值 × 4 |
| N | +(N−1) | 值 × N |

例：三个 `8`（内部值 3）合成 → 内部值 `3 + 2 = 5` → 显示 `32`，得分 `3 × 3 = 9`。

### 5.2 级联 `checkCombine()`

原实现是一个"每轮动画结束后再调一次"的循环，`GridView.animEnd()` 里：

```js
animEnd() {
  animInPlay--;
  if (animInPlay !== 0) return;
  if (GameModel.checkCombine()) return;   // 又合并了 → 等这批动画播完再来
  if (checkDead()) return;
  显示提示;
}
```

`checkCombine()` 的单轮流程：

1. `downArr` 为空就先跑 `checkDown()`；若发生了下落，**立刻 return false**（先播下落动画）。
2. 待判定集合 `checkArr = cur ∪ downArr`（去重），清空 `cur`。
3. 对集合里每个方块做一次 `checkBlockCombine`，把产生了合并的方块放进 `cur`。
4. `cur` 非空 → 说明还有合并，`saveBlocks()`，返回该方块（触发下一轮）。
5. `cur` 为空且上一轮有东西 → **级联结束**，结算连击、发奖、`combo = 0`。

### 5.3 连击 combo

* 每一轮 `checkBlockCombine` 成功都 `combo += 1`。
* 级联结束时，若 `combo >= 3` 弹出连击飘字（`SHOW_COMBO`），则播放 `combo_1..5` 音效与震动。
* `combo` 会累加到 `UserModel.todayCombineTimes`（用于每日任务）。
* 连击奖励金币：`addGold(cnt - 2)`。

## 6. 死亡与复活

```js
checkDead() {
  for (x = 0 .. 4) if (!getBlock(x, height - 1)) return false;   // 还有列没堆到 y=7
  触发 GAME_OVER;  return true;
}
```

> 注意：判定的是 **y = 7**，也就是**最靠近发射器的那一行**。堆到顶（y = 0）不算死。

复活 `relive()`：

```js
minValue = max(curMax - gap, 1)      // gap 见 §7.1
limit    = minValue + 2
清除所有 value <= limit 的方块
data.reliveCnt--
```

即复活会清掉棋盘上**一大片小方块**，只留较大的。初始 `reliveCnt = 2`。

## 7. `next` 方块生成算法（全游戏最复杂的一块）

玩家的下一个方块不是均匀随机的，而是一套**自适应权重**系统，
目的可以概括为：*给得出能合成的数字，但难度随棋盘高度上升*。

### 7.1 参数（`GameModel` 构造器）

```js
weights        = [15, 12, 9, 6, 3, 1]     // 基础权重（越小的值越容易出）
weightsAdd     = [0.15, 0.25, 0.35, 0.5, 0.4, 0.3]
weightsAddPow  = 1.3
extWeight      = 30                        // 棋盘上"低于下限"的值被额外拔高的权重
saveLevels     = [0, -1, -2, -3, -4]       // 保底补偿档位
saveWeights    = [10, 20, 30, 40, 50]
saveWeightsAdd = [20, 16, 12, 8, 4]
saveWeightsAddPow = 1.5
nextDiff       = [10, 2]                   // 避免连续给同一个值
nextDiffAdd    = [1, 1]
nextDiffAddPow = 1.5
```

随 `curMax`（历史最大内部值）变化的派生参数：

| 派生量 | curMax ≤ 10 | ≤13 | ≤14 | ≤16 | ≤17 | ≤21 | 其它 |
|---|---|---|---|---|---|---|---|
| `gap`（下限回退量） | 9 | 9 | 9 | 10 | 10 | 11 | 11 |
| `range`（候选个数） | 4 | 5 | 6 | 6 | 6 | 6 | 6 |
| `addWeightLimit`（触发保底的列高阈值） | 3 | 3 | 3.5 | 3.5 | 4 | 4 | 4 |
| `saveRange`（保底档位上限） | 1(≤8) / 2 | 3 | 3 | 4 | 4 | 5 | 5 |
| `saveAddMuti` | 1(≤8) / 0.85 | 0.7 | 0.7 | 0.55 | 0.55 | 0.4 | 0.4 |

`gap` 常量为 9/10/11，意味着**下一块最多只给 `curMax − 9`**。
当 `curMax = 8`（开局）时下限被 `max(...,1)` 拉回 1，候选就是 1..4（显示 2/4/8/16）。

### 7.2 流程（伪码）

```
min = max(curMax - gap, 1)
统计：cnt = 棋盘方块总数，meanValue = 平均内部值
addWeight = cnt / 5                     // 平均每列高度
baseAdd   = max(0, meanValue - min) ^ 1.3

values  = [min, min+1, ..., min+range-1]
weights = weights[0..range-1] + baseAdd * weightsAdd[0..range-1]
          // 棋盘平均值越高，越偏向给大一点的数字

arr = 棋盘上"临空"的方块（checkOut：下方或左右有空位 —— 也就是下一块可能落到它旁边）

if (addWeight >= addWeightLimit)        // 棋盘已经堆得比较高 → 开保底
    saveWeights[i] += addWeight^1.5 * saveWeightsAdd[i] * saveAddMuti
    saveIdx = randWeights(saveWeights)              // 抽一个补偿档位
    for (每个临空方块 b)
        if (b.value < min)  → 候选加上 b.value，权重 extWeight
        else                → v = b.value + saveLevels[saveIdx]
                              if (v 在 values 内)
                                  权重 = weights[v] * 1.5^(10/(1+b.y))
                                  // b.y 越小（越靠天花板）权重越高 → 优先照顾"贴顶的老方块"
else                                     // 棋盘还空 → 简单模式
    候选 = values，权重 = weights
    for (每个临空方块 b)
        if (b.value < min) 候选加上 b.value，权重 extWeight * 1.5^(10/(1+b.y))

// 避免连续重复
nextDiff[i] += addWeight^1.5 * nextDiffAdd[i]
if (randWeights(nextDiff) == 0 且候选 >= 2)
    从候选中删掉 == 上一手 data.next 的那个值

返回 按权重随机抽一个候选（randWeights 是"扫描累计"式加权随机）
```

### 7.3 设计意图（推断）

* **`gap = 9~11` 很大**，配合 `MAX_NUM = 32`，意味着 normally 给出的方块远小于棋盘最大值。
  玩家要靠"量"去凑，而不是总能拿到大数字 —— 这压低了爆分速度。
* **保底分支**（`addWeight >= addWeightLimit`）在棋盘堆高时启动，
  用 `saveLevels` 把棋盘上"临空的方块"数值**往小偏移**，制造"刚好能和你现有的块合成"的候选。
  `1.5^(10/(1+y))` 让靠天花板的方块获得更高权重 —— 因为那里的方块最难处理，需要优先送给它配对。
* **`extWeight = 30`** 远大于基础权重（15 起步），
  说明"把棋盘上过小的值再给一次"是很强的倾向（帮玩家清掉小数字）。
* **反重复**（`nextDiff`）概率随 `addWeight` 提升（`10 → 10 + addWeight^1.5`），
  越到后期越不会连续给同一个数字。

## 8. 道具与经济

`ToolType = { Back: 0, Hammer: 1, Swap: 2 }`

| 道具 | 价格 | 效果 | 实现位置 |
|---|---|---|---|
| 回退 Back | **20** 金币 | 把最后放入的方块收回发射器（`data.preX/preY` 记的那一块），动画是 `blockUp` 把它送回 y = height | `GameScene.toolBack` → `Grid.blockUp` → `GameModel.backBlock` |
| 锤子 Hammer | **200** 金币 | 最多敲碎 **`min(floor(方块数/2), 5)`** 个**数值最小**的方块，间隔 500ms 逐个敲 | `Grid.hammer` |
| 交换 Swap | **225** 金币 | 把棋盘上所有方块**两两随机配对交换**位置 | `Grid.swap` |

* 每个道具都可以用金币买，或消耗道具库存（`data.boosters[3]`，初始 `[0,0,0]`）。
* `useTool(type, withGold)`：有库存先扣库存；否则走 `useGold(toolGoldReq[type])`。
* 金币不足会触发 `NOT_EOUGH_GOLD` → Toast「金币不足！」。

### 8.1 金币来源（`UserModel`）

| 来源 | 数值 |
|---|---|
| 初始金币 | 300 |
| 看广告领金币 | `min(200, 150 + 25 × 当日已领次数)` |
| 连击奖励 | `cnt − 2`（cnt 为连击数） |
| 合成金币值（解锁弹窗用） | `min(200, 50 + 5 × (value − 9))` |
| 翻倍金币值 | `min(400, 250 + 10 × (value − 9))` |

### 8.2 每日任务

`todayCombineReq = [50,100,200,300,400,600,800,1000,1500,2000,2500,3000,4000,5000,6000,7000,8000,9000,10000,∞]`
—— 当日累计合成次数达到档位就弹奖励弹窗，并把目标抬到下一档。
`DateTool.isToday` 判跨天重置。注意 `DateTool.isToday` 的实现里有个坑：它比较的是今天的 0 点时间戳，
跨天时同时重置 `todayGoldAddTimes`、`todayCombineTimes`、`todayCombineTarget` 等。

## 9. 收集与解锁

* 每次合并成功都会 `UserModel.collect(newValue)` —— 给"合成出的内部值"计数（`data.collects`）。
* 顶部栏右侧的"下一目标方块"展示 `next = max(9, min(curMax + 1, 32))`：
  * 未收集过（计数 0）→ 显示「未解锁」
  * 已收集 → 显示 `xN`
* 第一次合成出新的最大值时触发 `REWARD_BLOCK` → 弹出「恭喜恭喜！再次合成了新的方块！」。
* 收集计数达到 `combineStartValue = 9` 以上才参与奖励判断。

## 12. 原版里的死代码与"文案落差"

逆向时发现的、复刻时值得注意的点：

1. **`DOUBLE_BLOCK` 事件从未被派发。**
   `GameEvent.DOUBLE_BLOCK` 有定义，`GameScene` 也监听了，
   `checkBlockCombine` 里还会设置 `this.toDoubleBlock`（当棋盘上恰好出现 2 个当前最大值且未到 32 时），
   但**全代码没有任何一处 `event(DOUBLE_BLOCK, ...)`**，`toDoubleBlock` 随后就被置空。
   「使用金币翻倍方块」的弹窗是遗留功能。本复刻因此也未实现。
2. **引导第 5 条「万能方块（可与任何数字合成）」未实现。**
   `getCombineArround` 只做 `b.value === target.value` 的严格相等判断，
   没有"∞ 可与任意数字合并"的分支。∞（内部值 32）只能与另一个 ∞ 合并。
   本复刻保持与原版一致。
3. **`UserModel.load()` 的一个细节**：`GameConf.DIRECT = data.direct` 用的是**未与默认值合并**的原始对象，
   首次运行时 `data = {}`，于是 `DIRECT = undefined`。因为判断都是 `DIRECT == -1`，
   `undefined == -1` 为 false，行为上等同 `DIRECT = 1`，所以没有暴露出来。复刻时直接固定为 1。
4. **`trackStartBox` 的 `sizeGrid` 为 `"12,0,45,0"`**（只做横向九宫格），
   而 `trackPrepare.png` 在原文里没有 sizeGrid。复刻按原样。
5. 广告、分享、云存档、埋点（`Analytics.dot`）都依赖平台 SDK（`ytgame` / `wx`），
   本复刻以占位实现替代。

### 13.1 移植时踩到的两个坑（供参考）

1. **Laya 的 `EventDispatcher.event(type, array)` 会把数组展开成多参数。**
   原代码大量使用 `event(BLOCK_COMBINE, [arr, combo])` 这种写法，
   对应回调签名是 `(blockDatas, combo)`。如果事件中心直接 `apply(ctx, [array])`，
   回调收到的就是一个数组，`blockDatas[0].id` 全是 `undefined`，会导致
   合并后新方块视觉体丢失、旧视觉体残留。
   复刻里 `EventCenter.event` 明确按"数组即展开"实现（`src/util.js`）。

2. **`Grid.newBlock` 必须写坐标。**
   `createBlock(blockData)` 之后要 `block.vx = blockData.x; block.vy = blockData.y;`。
   漏掉的话，所有通过 `addNewBlock` 放置的方块（**引导关卡和读档恢复**都走这条路）
   会全部堆在 (0,0) 单元格。

## 14. 平衡性模拟

用贪心 AI（优先选能立刻与同值相邻的列，否则选最矮的列）跑 30 局：

| 指标 | 结果 |
|---|---|
| 平均分 | 约 11,000 |
| 最高分 | 约 20,000 ~ 26,000 |
| 平均最大方块（内部值） | 约 13.6 → 显示约 **8K~16K** |
| 单局最大方块 | 17 → **128K** |
| 平均步数 | 约 1,190 步 |

解读：
* 因为 `gap = 9~11` 且 `MAX_NUM = 32`，**达到 2048（内部值 11）并不算难**，
  真正的长线目标是 12 以上（4K / 8K / …）。
* 单局动辄上千步，属于**长局慢热**的节奏，与"一次合成数字翻倍"的强反馈形成对比。
* `DOT_SCORE` 最高档位 100000，配合平均 11000 分，说明那是给顶尖玩家准备的里程。
